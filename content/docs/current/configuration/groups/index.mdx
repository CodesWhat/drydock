A group policy is an update policy that Drydock stores for one named group. Every container in that group inherits it, including containers that join the group later, so you set a rule once instead of labeling each container.

<Callout type="info">Group policies are on the unreleased v1.8 development line. This page describes the update-policy fields and the API. A group policy does not restrict or grant any action, and it does not change notification routing.</Callout>

## What a group is

Drydock derives a container's group from its labels, in this order: `dd.group`, then `com.docker.compose.project`, then `com.docker.stack.namespace`. A container with none of them has no group and no group policy. This is the same identity [notification group routing](/docs/configuration/triggers#route-notifications-to-a-group) and `GET /api/v1/containers/groups` use.

- Names match exactly. Case, whitespace and punctuation count, and nothing is trimmed or normalized.
- An empty `dd.group` does not fall through to the Compose project. A container with `dd.group=""` has the group `""`, which can't carry a policy, so that is the way to opt one container out of its Compose project's policy.
- Matching is fleet-wide by name. A policy for `payments` reaches every container in that group on the controller and on every agent. If two hosts need different policies, give their containers different `dd.group` values.
- The browser's "Set group" override is a display preference. It never changes which policy applies.

## What a policy sets

A policy carries the four declarative update-policy fields, with the same values the `dd.updatePolicy.*` labels accept:

| Field | Values |
| --- | --- |
| `maturityMode` | `all` or `mature` |
| `maturityMinAgeDays` | integer from 1 to 365 |
| `skipTags` | list of tags to skip |
| `skipDigests` | list of digests to skip |

A policy has to set at least one field. An empty `skipTags` or `skipDigests` list is dropped, because the only layer below a group is the watcher environment, which has no skip lists. `maturityMode: all` is kept, since it deliberately overrides a watcher default of `mature`. `snoozeUntil` is not a group field: a snooze stays a per-container override.

## Precedence

Each field resolves on its own, and the last layer that sets it wins:

| Priority | Layer | Example |
| :---: | --- | --- |
| 1 (highest) | UI/API override | `PATCH /api/v1/containers/:id/update-policy` |
| 2 | Container label | `dd.updatePolicy.maturityMode=all` |
| 3 | **Group policy** | `PUT /api/v1/group-policies/:id` |
| 4 | Watcher environment | `DD_WATCHER_LOCAL_MATURITY_MODE` |
| 5 (lowest) | Built-in | `maturityMode=all`, empty skip lists |

Skip lists replace the lower layer's list instead of being added to it. The container's `updatePolicySources` names the layer each field came from, and `group` is one of the values. The container response also carries `groupPolicy`, a snapshot of the policy (id, group, revision and values) it was last resolved against.

A label or an override on a member still wins over the group for the same field, so a group policy is a default for the group, not a lock. Whoever controls a container's labels, including `dd.group`, controls whether the group policy reaches it. Don't treat a group policy as a security boundary.

Existing override actions work the same against the new layer. `revert-to-declarative` removes an override and reveals the label, then the group, then the watcher value. `skip-current` copies the effective skip list, group values included, into the override, so later edits to the group's list no longer reach that field on that container until you revert it.

## Membership changes

Membership is worked out from the container's current labels every time Drydock writes the container.

- A container that joins a group gets its policy on its next write, and a policy write re-resolves every current member immediately.
- A container that leaves a group, or whose group's policy is deleted, loses those values. Its fields fall back to label, watcher or built-in values. Nothing from the old group is carried over.
- Overrides belong to the container, so they survive both, including when Docker recreates the container. A recreated container picks up the policy of whichever group its new labels name.

## API

Reads need the `read` scope. Writes need `admin`, because one write changes every current and future member of the group. A `containers:update` key can still set per-container overrides but can't write a group policy. Group names aren't URL-safe, so policies are addressed by `id`.

```bash
# Create
curl -X POST http://drydock:3000/api/v1/group-policies \
  -H 'Content-Type: application/json' \
  -d '{"group":"payments","updatePolicy":{"maturityMode":"mature","maturityMinAgeDays":14}}'
```

```json
{
  "policy": {
    "id": "5b0d7c2e-4f6a-4c55-9a53-0a1f6f1f3c11",
    "group": "payments",
    "revision": 1,
    "updatePolicy": { "maturityMode": "mature", "maturityMinAgeDays": 14 },
    "actions": {},
    "createdAt": "2026-10-03T12:00:00.000Z",
    "createdBy": "user:admin",
    "updatedAt": "2026-10-03T12:00:00.000Z",
    "updatedBy": "user:admin"
  },
  "applied": { "members": 3 },
  "warnings": []
}
```

| Request | Scope | Notes |
| --- | --- | --- |
| `GET /api/v1/group-policies` | `read` | Every policy with `members: { count, agents }`. `agents` lists the hosts, with `null` for the controller |
| `GET /api/v1/group-policies/:id` | `read` | One policy with its members, or 404 |
| `POST /api/v1/group-policies` | `admin` | Body `{ group, updatePolicy }`. Returns 201, or 409 when the group already has a policy |
| `PUT /api/v1/group-policies/:id` | `admin` | Full replace. Body `{ revision, updatePolicy }`, with an optional `group` that must match the stored one |
| `DELETE /api/v1/group-policies/:id?revision=N` | `admin` | Deletes the policy and re-resolves its members |

Things worth knowing:

- `revision` guards against lost updates. Send the revision you read. A stale one gets a 409 and writes nothing, so reload the policy and apply the change again.
- A `PUT` that matches the stored policy returns `changed: false`, writes nothing, doesn't bump the revision and isn't audited.
- The group is immutable. A `PUT` with a different `group` is a 400. Delete the policy and create one for the new group.
- `applied.members` counts the stored container records that were re-resolved, on the controller and on agents, connected or not. A policy for a group with no current members still saves, with a warning that it applies to future members.
- Unknown fields are rejected with a 400. That includes `actions`, which isn't accepted yet.
- If re-resolving members fails after the policy was saved, the response carries a warning instead of an error. Members pick the policy up on their next write, and Drydock reconciles them at startup.

## Audit

Creating or replacing a policy records `group-policy-set`, and deleting one records `group-policy-cleared`. The entry's container name is the exact group name, and its details are JSON with the policy id, the group, the operation (`created`, `replaced` or `deleted`), the revision, who made the change (`user:<name>` or `api-key:<keyId>`), the changed fields as `before` and `after`, and the member count. The policy row and its audit row are written in one transaction, so a saved change is always audited and an audited change is always saved. Rejected requests aren't audited.

Per-container override audit entries (`update-policy-override-set` and `update-policy-override-cleared`) also carry the group layer's value for each field, next to the env and label values.

## Agents

Policies live on the controller and are applied there. Containers reported by an agent get their group from the labels the agent reports, and the controller adds the group layer when it stores them. Agents don't receive policies and the policy routes aren't mounted on the agent API.
