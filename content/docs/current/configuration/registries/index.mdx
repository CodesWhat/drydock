<Callout type="info" title="Naming registry instances">
Registry env vars use the pattern `DD_REGISTRY_<TYPE>_<INSTANCE>_<KEY>` — the `<INSTANCE>` part (shown as `{REGISTRY_NAME}` in tables on the pages below) is a label you pick. It lets you register multiple instances of the same registry type (e.g. one private GHCR account plus the public one). Existing examples use `PUBLIC` for Docker Hub and `PRIVATE` for GHCR:

```yaml
- DD_REGISTRY_HUB_PUBLIC_LOGIN=myuser
- DD_REGISTRY_HUB_PUBLIC_PASSWORD=dckr_pat_xxx
- DD_REGISTRY_GHCR_PRIVATE_USERNAME=myuser
- DD_REGISTRY_GHCR_PRIVATE_TOKEN=ghp_xxx
```

Pick whatever label is meaningful for you — `PRIVATE`, `WORK`, `MYCO` all work. The label is internal-only; it never appears in image references.
</Callout>

<Callout type="info">By default, without any further configuration, drydock handles _out-of-the-box_ public images hosted on

## Registry routing

When multiple instances of the same registry type are configured (one anonymous and one credentialed), drydock gives explicit priority to credentialed instances. The previous silent anonymous fallback on 401/403 is removed — an auth rejection now surfaces as an actionable "Check failed" badge in the UI instead of silently retrying as a public caller.

<Callout type="warn" title="Credentialed instances take priority">
If you configure both a credentialed and an anonymous instance of the same registry type, drydock will always route image lookups through the credentialed instance. There is no label or setting to pin a specific container to the anonymous instance instead; when more than one instance matches an image, the credentialed one always wins, and among instances of the same tier (credentialed or anonymous) the one whose `{INSTANCE}` name sorts first alphabetically is used.
</Callout>

## Rate limiting and retry

drydock applies a per-host token bucket to most outbound registry calls and automatically retries on 429 and 503 responses. Default rates:

| Host | Rate | Burst |
| --- | --- | --- |
| `ghcr.io` | 2 req/s | 10 |
| `registry-1.docker.io` (Docker Hub) | 2 req/s | 10 |
| `api.github.com` | 1 req/s | 3 |
| `public.ecr.aws` | 2 req/s | 10 |
| All other hosts | 5 req/s | 10 |

GHCR's publish-date lookup (used to populate `getImagePublishedAt`) calls the GitHub packages API directly and does not go through this bucket, so it is not subject to the `api.github.com` rate above.

On a 429 or 503 response, drydock honors the upstream `Retry-After` header (both seconds and HTTP-date forms) and falls back to exponential backoff (1 s → 2 s → 4 s, capped at 60 s), up to 3 retries per call.

<Callout type="info">The rate limiter works alongside the watcher cron default of `0 */6 * * *` (every 6 hours). High-container-count deployments (40+ containers with many-page tag lists) benefit most from leaving the 6-hour default in place. See [Watcher cron and rate limits](/docs/configuration/watchers#variables) for guidance.</Callout>

## TLS and insecure registries

Registry instances configured with `INSECURE=true` (TLS certificate validation disabled) emit a **warn-level log on every request** as a reminder that certificate validation is off. This log fires for each outbound call, so it is visible in normal `docker logs drydock` output.

Use `INSECURE=true` only for self-hosted registries on private networks where a valid TLS certificate cannot be provisioned. For production registries reachable over the internet, always use a valid certificate.

Registry TLS settings apply end to end. `DD_REGISTRY_*_CAFILE`, `_CLIENTCERT`, `_CLIENTKEY`, and `_INSECURE` are used for credential/token requests, tag-list requests, manifest and blob lookups, and anonymous provider paths. A private CA, mTLS client key pair, or insecure override therefore affects the entire registry lookup flow rather than only the initial login/token exchange.

## Outbound proxy

Registry traffic can go through an HTTP or HTTPS forward proxy. This covers tag-list and manifest requests, Bearer token exchange, and the Docker Hub and GHCR publish-date lookups. HTTPS registries are reached through an HTTP `CONNECT` tunnel, so authenticating proxies work, and the registry's `CAFILE`, `CLIENTCERT`, `CLIENTKEY` and `INSECURE` settings still apply inside the tunnel.

Set a proxy for one registry with `DD_REGISTRY_{type}_{name}_PROXY`, or for all registry traffic with environment variables:

| Variable | Description |
| --- | --- |
| `DD_REGISTRY_{type}_{name}_PROXY` | Proxy URL for this registry only, for example `http://user:pass@proxy.internal:3128`. Wins over the global variables. Must be `http://` or `https://`. |
| `DD_HTTPS_PROXY` | Proxy for `https://` registries. Falls back to `HTTPS_PROXY` / `https_proxy`. |
| `DD_HTTP_PROXY` | Proxy for plain `http://` registries. Falls back to `HTTP_PROXY` / `http_proxy`. |
| `DD_NO_PROXY` | Comma-separated hosts that bypass the proxy. Falls back to `NO_PROXY` / `no_proxy`. |

`DD_NO_PROXY` entries match the host and its subdomains (`example.com` and `.example.com` both match `registry.example.com`), `host:port` pins a port, and `*` disables proxying. It applies to the per-registry `PROXY` too. CIDR ranges are not supported.

```yaml
services:
  drydock:
    environment:
      - DD_HTTPS_PROXY=http://proxy.internal:3128
      - DD_NO_PROXY=registry.lan,.corp.example.com
      - DD_REGISTRY_CUSTOM_PRIVATE_URL=https://registry.corp.example.com
      - DD_REGISTRY_CUSTOM_PRIVATE_PROXY=http://svc:${PROXY_PASSWORD}@proxy.internal:3128
```

Credentials in a proxy URL are masked as `[REDACTED]` in the registration log and in the API configuration output, and error messages never include them. URL-encode special characters in the username or password (`@` becomes `%40`). The proxy settings apply to registry traffic only. Amazon ECR's token request uses the AWS SDK and is not routed through the proxy.

## Automatic Bearer token exchange

When a registry responds to a tag-list or manifest request with `401 Unauthorized` and a `WWW-Authenticate` header containing a `Bearer realm=…,service=…,scope=…` challenge, drydock automatically performs the standard Docker Registry v2 token-auth flow: it fetches a token from the realm endpoint (anonymously for public images, or with the configured credentials for private ones) and retries the request once. The Bearer challenge can appear alongside other schemes such as `Basic`, and token responses may use either `token` or `access_token`.

This covers registries that do not require a pre-authenticated session, including:

- Public images on **Codeberg** (`codeberg.org`) and other Forgejo/Gitea instances
- **Chainguard** (`cgr.dev`) and other registries that always challenge before serving tag lists

The realm authority is validated against the registry's own configured authority before any credentials are sent, including non-default ports. The exchange is silently skipped if the challenge points to an untrusted host or port, and the original 401 is returned instead. If credentials were configured and the trusted token endpoint rejects them with `401` or `403`, drydock surfaces a credential-specific authentication error instead of falling back to the original registry 401. Providers that already perform proactive Bearer auth (GHCR, Docker Hub, Quay) are unaffected.

## Registry lookup image (`dd.registry.lookup.image`)

The `dd.registry.lookup.image` container label redirects tag and manifest queries to an alternative image reference (e.g. check Docker Hub's `library/nextcloud` for a container running from a private mirror). In v1.5.0, this substitution is applied only at query boundaries (`getTags`, `getImageManifestDigest`, `getImagePublishedAt`) and no longer overwrites the container's deploy identity (`image.name`, `image.registry.url`). This means compose-file rewrites and container recreates always use the original image, not the lookup target.

Un-prefixed images (e.g. `nginx:1.0`) now default to `docker.io` for the registry URL.

### Locally built images (base image updates)

An image you build on the host and never push has no registry copy, so Drydock normally skips the registry lookup for it and reports no update. Set `dd.registry.lookup.image` to the upstream base you built from and Drydock looks that image up instead. The tag of your local image is treated as the base version it was built from (for example a local `myapp:1.25.0` built `FROM nginx:1.25.0` with `dd.registry.lookup.image=library/nginx`), so a newer tag of the base is reported as an update. The pin gate and strict floating-alias rules do not apply to these images, because there is no registry digest to compare against. `dd.tag.include`, `dd.tag.exclude` and `dd.tag.transform` still apply.

The update is labelled a **base image update** (`updateKind.baseImage` is `true` in the API, with `kind` still `tag`), and the default notification title and body say so. It is notification-only. The Docker and Docker Compose actions never run for a locally built image, automatically or by hand, because pulling the upstream base would replace your build with the stock image. The update button is refused with a `409`, and automatic dispatch skips the container.

To act on the update, ask your CI to rebuild with the [GitHub Dispatch](/docs/configuration/triggers/githubdispatch) or [GitLab Pipeline](/docs/configuration/triggers/gitlabpipeline) trigger, or wire a rebuild yourself with a [command action](/docs/configuration/triggers/command), which is not blocked. Point it at your own rebuild script and include the container, for example:

```yaml
services:
  myapp:
    build: .
    image: myapp:1.25.0
    labels:
      - dd.registry.lookup.image=library/nginx
      - dd.action.include=rebuild
```

```bash
DD_ACTION_COMMAND_REBUILD_CMD=/scripts/rebuild.sh "${display_name}" "${update_kind_remote_value}"
```

The script should rebuild with the new base (`docker compose build --pull myapp && docker compose up -d myapp`, or your CI). Drydock does not rebuild images for you.
