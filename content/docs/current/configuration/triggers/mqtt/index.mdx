The `mqtt` trigger lets you send container update notifications to an MQTT broker.

## Variables

<Callout type="info">This trigger also supports the [common configuration variables](/docs/configuration/triggers/#common-trigger-configuration). but only supports the `simple` mode.</Callout>

<Callout type="info">**Home Assistant entity stability:** When a watched container is recreated during an update, the MQTT HASS sensor (`binary_sensor`) is preserved without an intermediate unavailable/disappear state. Drydock sets a `replacementExpected` flag before stopping the old container so the entity remains visible in Home Assistant throughout the update.</Callout>

<Callout type="info">You want to customize the name & icon of the Home-Assistant entity?
[Use the `dd.display.name` and `dd.display.icon` labels](/docs/configuration/watchers/#labels).</Callout>

<Callout type="info">For Home Assistant, the `entity_picture` is automatically derived from the `dd.display.icon` label. Icons with `sh:`, `hl:`, or `si:` prefixes map to CDN image URLs. You can also set `dd.display.picture` to provide a direct URL override.</Callout>

<Callout type="warning">**Multi-agent deployments:** Home Assistant MQTT topics include an `agent/<name>` segment for agent-owned containers by default as of v1.7.0, scoping topics, watcher running-status, sensor counts, and discovery cleanup per agent so multiple agents sharing the default watcher name `local` no longer collide. This changed the Home Assistant entity IDs for agent containers on upgrade — update any automations or dashboards that reference the old (agent-less) entity IDs. Drydock does not retroactively remove the old discovery entities; they remain retained on the broker and show up as orphaned, frozen-at-last-state duplicates until manually removed. Set `DD_NOTIFICATION_MQTT_{trigger_name}_HASS_AGENTTOPICSEGMENT=false` to temporarily opt back into the pre-v1.7.0 unscoped layout — see [Deprecations](https://getdrydock.com/docs/deprecations). Toggling `HASS_AGENTTOPICSEGMENT` in either direction moves the retained state topic and the old one is not cleared automatically, because the unscoped topic can legitimately belong to a controller-local container of the same name and drydock cannot tell that case apart from a stale one. If you flip the setting, publish an empty retained message to the old topic yourself to clear it.</Callout>

<Callout type="warning">**Topics and `unique_id` are keyed by container identity as of v1.8.0.** The state topic segment (`{container}` below) is the Compose `project.service` pair for a container carrying `com.docker.compose.project`/`com.docker.compose.service` labels, and the sanitized container name otherwise — so `<topic>/<watcher>/<container>` is `dd/container/local/myapp.web`, not `dd/container/local/myapp_web_1`. The Home Assistant `unique_id` no longer comes from the topic at all: it's `dd_` plus a hash of the container's identity. **Rename stability of both the topic and the `unique_id` is a guarantee for Compose-labeled containers only** — a container with no `com.docker.compose.*` labels is identified by its name, so renaming it still changes its topic and (barring a carried-over stored identity) its `unique_id`, the same as before v1.8.0. Update any hand-written subscriptions to the new topic shape. Existing Home Assistant entities repair themselves automatically the first time a v1.8.0 controller starts — see [Deprecations](https://getdrydock.com/docs/deprecations).</Callout>

## Home Assistant devices

As of v1.8.0 each watched container gets its own Home Assistant device. Its
identifier is `drydock_` plus the container's `unique_id`, its name is the
container's display name, its model is the image name, and `via_device` points
at the `drydock` device, so Home Assistant nests the containers under drydock on
the integration page. The drydock-level entities stay where they were: global
container counts, per-watcher counts, and watcher running status all remain on
the `drydock` device.

**Migration is automatic and keeps your history.** The discovery config topic and
the `unique_id` are unchanged by this, so the retained payload drydock publishes
on startup is a discovery *update* for the entity that already exists rather than
a new entity: entity ids, unique ids, and history are preserved. Existing entities
move to their container device after you reload the MQTT integration (Settings,
Devices and services, MQTT, three dots, Reload) or restart Home Assistant; new
containers appear under their own device immediately. Nothing is orphaned and no
entities need to be removed by hand.

Two things do change visibly. Each container's update entity moves off the
`drydock` device onto its own, so anywhere Home Assistant shows a device next to
an entity you now see the container. And friendly names get shorter: Home
Assistant prefixes every discovered entity's name with its device's name, so the
update entity is published unnamed (Home Assistant's marker for the device's main
feature) and shows as `nginx` rather than the `drydock nginx` you had before, or
`nginx nginx` if it kept its own name. `dd.display.name` now names the device;
`dd.display.icon` and `dd.display.picture` still apply to the entity.
Automations that address entities by entity id are unaffected. Anything that
targets the `drydock` *device* (a device trigger, or a `device_id`-based action)
now only reaches the drydock-level entities and has to be re-pointed at the
container's device or at the entity directly.

Set `DD_NOTIFICATION_MQTT_{trigger_name}_HASS_DEVICEPERCONTAINER=false` to keep
the pre-v1.8.0 layout, where every entity sits on the single `drydock` device.

### Install button (bidirectional commands)

Set `DD_NOTIFICATION_MQTT_{trigger_name}_HASS_COMMANDS=true` to let Home Assistant trigger container updates back, not just observe them. When enabled, drydock adds a `command_topic` to each container's discovery payload (`{state_topic}/cmd`), so the update entity's Install button becomes clickable in the HA UI. Clicking it publishes the literal payload `install` to that topic; drydock subscribes to it and runs the same update path the `/update/:containerName` webhook uses, including trigger resolution, agent routing, and every existing eligibility check (no update available, active operation in progress, rollback blockers, and so on).

A few things worth knowing before you turn this on:

- `HASS_COMMANDS` needs `HASS_ENABLED`, but not `HASS_DISCOVERY`. If you've hand-configured your own HA `update` entity pointing at drydock's command topic convention (`{topic}/{watcher}/{container}/cmd`, or `{topic}/agent/{agent}/{watcher}/{container}/cmd` for agent-owned containers), commands work without drydock ever publishing discovery messages itself. `{container}` is the identity-based segment described above (the Compose `project.service` pair, or the sanitized container name), as of v1.8.0.
- Each container is rate-limited to one accepted command every 30 seconds. Repeated clicks within that window are dropped silently on drydock's side; this isn't configurable yet.
- Commands only work while drydock is connected to the broker. The MQTT connection is a clean (non-persistent) session, so a click sent while drydock is offline or reconnecting doesn't queue up and replay later, it's just lost.
- If two containers somehow sanitize down to the same state topic, drydock refuses to guess and drops the command rather than updating the wrong one.
- Since anyone who can publish to a container's command topic can trigger an update, scope your Home Assistant broker credential tightly: publish-only access to `{topic}/+/+/cmd` and `{topic}/agent/+/+/+/cmd` is all it needs.

### Update progress

Once an update is running, drydock reports how far along it is on the same state topic the entity already reads, so the Install button shows a live progress bar instead of sitting there until the next watch cycle. The container's state payload carries an `update_state` object with Home Assistant's own `installed_version`, `in_progress` and `update_percentage` fields, and the entity's `value_template` hands that object straight to HA.

The percentage is a fixed ladder over the phases an update walks, not a measurement: pulling the image reports 10, the image scan 30, preparing the new container 40, renaming 50, creating 60, stopping the old one 70, starting the new one 80, and the health gate 85 through 95. A rollback reports 90. Drydock has no byte-level progress from the registry pull to work with, so these numbers tell you which step is running, not how much time is left.

When the operation finishes, drydock publishes `in_progress: false` with a null percentage and the entity returns to its normal state. That happens on every outcome, so a failed or rolled-back update clears the progress bar exactly like a successful one; the installed and newest versions keep whatever the container itself reports. Progress is derived from the live operation each time drydock publishes, so a restart part-way through an update can't leave an entity spinning forever.

This needs `HASS_ENABLED`, but not `HASS_DISCOVERY`. If you hand-configured your own `update` entity, point its `value_template` at the new object to pick progress up:

```yaml
value_template: >-
  {% if value_json.update_state is defined %}{{ value_json.update_state | to_json }}{% else %}{{ value_json.image_tag_value }}{% endif %}
```

<Callout type="info">**Existing payloads keep working.** `update_state` is added to the state payload, nothing was removed or renamed, and the template falls back to the old behaviour for a retained message published by an older drydock. Home Assistant only reads `in_progress` and `update_percentage` from the object the `value_template` renders, so a template that emits a bare version string ignores them.</Callout>

## Attribute filtering

Container MQTT payloads can include large nested fields (SBOM documents, scan vulnerability arrays, environment details, labels) that exceed Home Assistant's `json_attributes_topic` size limits or clutter entity attributes.

Filtering is applied in this precedence order:

1. `HASS_FILTER_INCLUDE` (flattened key include list)
2. `HASS_FILTER_EXCLUDE` (flattened key exclude list)
3. `EXCLUDE` (legacy nested dot-path exclude list)
4. `HASS_ATTRIBUTES` preset fallback

### Include mode (`HASS_FILTER_INCLUDE`)

Set `DD_NOTIFICATION_MQTT_{trigger_name}_HASS_FILTER_INCLUDE` to keep only selected flattened keys.

```yaml
environment:
  - DD_NOTIFICATION_MQTT_MOSQUITTO_HASS_FILTER_INCLUDE=name,image_name,update_available,result_tag
```

### Exclude mode (`HASS_FILTER_EXCLUDE`)

Set `DD_NOTIFICATION_MQTT_{trigger_name}_HASS_FILTER_EXCLUDE` to remove selected flattened keys.

```yaml
environment:
  - DD_NOTIFICATION_MQTT_MOSQUITTO_HASS_FILTER_EXCLUDE=security_sbom_documents_0_spdx_version,security_scan_vulnerabilities_0_id
```

### Legacy nested exclude (`EXCLUDE`)

`DD_NOTIFICATION_MQTT_{trigger_name}_EXCLUDE` still supports comma-separated nested dot-paths (for example `security.sbom.documents,labels`). This legacy filter is only used when `HASS_FILTER_INCLUDE` and `HASS_FILTER_EXCLUDE` are both empty.

### Attribute preset fallback (`HASS_ATTRIBUTES`)

When no explicit include/exclude list is configured, `HASS_ATTRIBUTES` is used:

| Preset | Behavior |
| --- | --- |
| `full` | Sends the entire container object — no filtering |
| `short` (default) | Excludes `security.sbom.documents`, `security.updateSbom.documents`, `security.scan.vulnerabilities`, `security.updateScan.vulnerabilities`, `details`, and `labels` |

<Callout type="info">`HASS_FILTER_INCLUDE` and `HASS_FILTER_EXCLUDE` match flattened MQTT keys (snake_case + underscore delimiter), because filtering is applied after flattening to the payload shape Home Assistant receives.</Callout>
